PART 00

先搞懂三件事，再動手

這套系統由三個獨立的零件組成。把它們分開理解，後面每一步你都會知道自己在做什麼。

零件負責什麼對應 Firebase 服務
託管把網頁放到一個會「執行」它、給你 https 網址的地方Hosting
登入用 Google 帳號確認「你是誰」Authentication
核准記錄每個人的狀態，只有 approved 能看內容Firestore + 安全規則

使用者的旅程是這樣的，你要做的就是在後台把 pending 改成 approved：

🛡️

資安關鍵（請先讀）：真正的把關必須在後端（Firestore 安全規則）強制執行。前端 JavaScript 的判斷只是「畫面控制」，任何人打開開發者工具就能繞過。本手冊的規則會做到：使用者無法把自己改成 approved，沒核准就讀不到受保護資料。

PART 01

建立 Firebase 專案

所有東西都掛在一個「專案」底下。先用你的 Google 帳號開一個。

1

進入 Firebase Console

到 console.firebase.google.com，用你的 Google 帳號登入，點「建立專案 / Add project」。

2

命名與建立

取個名字（例如 satir-lab）。Google Analytics 這次可以關掉，省事。按建立，等個幾十秒。

3

註冊一個 Web App，拿到金鑰

專案首頁中央有幾個圖示，點那個 </>（Web） 圖示。取個暱稱、勾選「也設定 Firebase Hosting」，按註冊。接著畫面會給你一段 firebaseConfig——把它複製下來，等等要用。長這樣：

你的 firebaseConfig（範例）
const firebaseConfig = {
  apiKey: "AIzaSyA...你的金鑰",
  authDomain: "satir-lab.firebaseapp.com",
  projectId: "satir-lab",
  storageBucket: "satir-lab.appspot.com",
  messagingSenderId: "1234567890",
  appId: "1:1234567890:web:abc123def456"
};
💡

資安人請放心：這段 apiKey 不是密碼，可以公開，它只是用來識別你的專案。整套系統的安全性靠的是後面的「Firestore 安全規則」，不是藏住這把 key。這是 Firebase 新手最常見的誤解。

PART 02

開啟 Google 登入

讓使用者能用 Google 帳號登入，這是辨識「他是誰」的依據。

1

啟用 Authentication

左側選單 Build → Authentication，按「開始使用」。切到 Sign-in method 分頁。

2

啟用 Google 提供者

在清單裡點 Google → 打開 Enable → 選一個對外的支援信箱 → 儲存。完成後 Google 那列會顯示「已啟用」。

3

記得授權網域

同頁的 Settings → Authorized domains 預設已含你的 *.web.app。之後若綁自訂網域，要回來把網域加進這份清單，否則登入會被擋。

PART 03

建立 Firestore 資料庫

這裡存放每個人的核准狀態。我們用一個 users 集合，每位使用者一筆資料。

1

建立資料庫

左側 Build → Firestore Database → 「建立資料庫」。地點選離你近的（如 asia-east1）。模式先選 Production mode（正式模式）——我們等等會自己寫規則。

2

資料結構（不用手動建，登入時程式會自動寫入）

每位使用者會是 users 集合底下、以他的 uid 為 ID 的一筆文件：

Firestore 資料示意
users/
  └─ aBc123XyZ...（使用者的 uid）
       ├─ email:       "someone@gmail.com"
       ├─ name:        "某人"
       ├─ status:      "pending"   // pending | approved | blocked
       ├─ requestedAt: 2026-06-09T...
       └─ approvedAt:  null
✓

三種狀態：pending 剛申請、等你審；approved 你已放行；blocked 你拒絕或封鎖。只有 approved 看得到內容。

PART 06

安全規則：真正的鎖在這裡

這是整套系統的命脈。它在 Google 的伺服器端強制執行，前端怎麼改都繞不過。到 Firestore Database → Rules 分頁，把內容整段換成下面這份。

Firestore 安全規則
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // 把這裡換成「你自己」的管理員 Email（可多個）
    function isAdmin() {
      return request.auth != null
        && request.auth.token.email in [
          "你的email@gmail.com"
        ];
    }

    match /users/{uid} {
      // 本人或管理員可讀
      allow read: if request.auth != null
                  && (request.auth.uid == uid || isAdmin());

      // 只能建立「自己的」申請，且狀態強制為 pending、email 必須是本人
      // → 防止有人直接把自己建成 approved
      allow create: if request.auth != null
                    && request.auth.uid == uid
                    && request.resource.data.status == 'pending'
                    && request.resource.data.email == request.auth.token.email;

      // 只有「管理員」能改狀態（核准 / 封鎖）；一般人完全不能改自己的狀態
      allow update: if isAdmin();
      allow delete: if isAdmin();
    }

    // （進階）若把受保護內容存在 Firestore，只有 approved 讀得到
    match /protected/{docId} {
      allow read: if request.auth != null
        && exists(/databases/$(database)/documents/users/$(request.auth.uid))
        && get(/databases/$(database)/documents/users/$(request.auth.uid)).data.status == 'approved';
      allow write: if isAdmin();
    }
  }
}
🔑

這份規則達成三件事：① 使用者只能替自己建立申請，而且只能建成 pending；② 只有名單上的管理員 Email 能把人改成 approved；③ 一般人讀不到別人的資料、也改不動自己的狀態。把 你的email@gmail.com 換成你的 Google 信箱後，按「發布 / Publish」。

PART 08

你要怎麼核准別人？

有人申請後，你把他的 status 從 pending 改成 approved 即可。兩種做法，挑一個。

方法 A ‧ 零程式（推薦先用這個）

直接在 Firebase Console 改。Firestore Database → 資料 → users 集合，點開那筆申請，把 status 欄位的值從 pending 改成 approved，存檔。對方重新整理頁面就進得來了。單人營運、申請量不大時，這最省事。

💡

Console 用的是管理權限，不受安全規則限制，所以你在這裡永遠改得動。要封鎖某人就把 status 改成 blocked。

方法 B ‧ 做一個核准管理頁

PART 09

綁網域、費用、常見問題

主題說明
綁自訂網域Hosting → 新增自訂網域，照指示到你的 DNS 加紀錄。完成後務必回 Authentication → Authorized domains 把網域加進去，否則 Google 登入會失敗。
費用Hosting 與 Firestore 都有免費額度（Spark 方案）。一份學習單、幾百到幾千次存取，通常完全免費。流量爆大才需要升級。
登入跳出後沒反應多半是 popup 被瀏覽器擋，或網域不在 Authorized domains。先看主控台 console 的錯誤訊息。
改了規則沒生效規則要按「Publish」才會套用；前端有時要清快取或開無痕視窗重試。
想限定只有某公司網域可在 gate 裡多判斷 user.email.endsWith("@yourorg.com")，並在規則的 create 條件比照加上。
PART 10 ‧ 給資安人的加固清單

把它做得更硬

你是做紅隊的，這幾條應該對你的胃口。前面的版本已能擋掉一般人，這裡是把攻擊面再收窄。

🛡️ 加固檢查清單（點擊勾選）

規則是唯一真相。前端 gate 只是 UX。永遠假設前端會被繞過，把所有「誰能讀什麼」寫死在 Firestore Rules 裡。
別把機密內容放純前端。放在 public/ 的 app.html 一旦知道路徑就能直連、原始碼也看得到。真要鎖內容，把它存進 Firestore protected 集合，用規則擋成「只有 approved 能讀」，前端登入後才抓回來渲染。
開啟 App Check。Firebase 的 App Check（reCAPTCHA Enterprise）能擋掉非從你網站發出的偽造請求，大幅降低被腳本濫用 API 的風險。
apiKey 公開沒關係，但要鎖用途。到 Google Cloud Console 的「憑證」把這把 API key 限制 HTTP 來源（只允許你的網域）與可用 API，避免被挪用。
最小權限原則。規則裡除了 users 和 protected，其餘一律預設拒絕（不寫 match 就是拒絕）。別圖方便開 allow read, write: if true。
定期稽核名單。偶爾掃一遍 users 集合，清掉不再需要的 approved；可加 expiresAt 欄位做「到期自動失效」（在規則裡比對 request.time）。
用 Rules 模擬器測試。Firestore Rules 分頁內建 Playground，發布前模擬「未登入 / pending 使用者 / 別人冒充」各種情境，確認都被擋。
升級版核准用 Custom Claims。規則裡寫死 admin email 很實用；要更嚴謹可改用 Firebase Custom Claims（request.auth.token.admin == true），透過 Cloud Functions 指派，避免 email 比對的邊角風險。
