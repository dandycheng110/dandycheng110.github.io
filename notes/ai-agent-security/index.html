AGENTIC AI · DEFENSE BRIEFING
v2026.1 · 機密等級：公開
如何對 AI Agent 做資安防禦

假設模型
隨時會被操弄。

AI agent 與傳統應用最大的不同，是它會自己規劃、呼叫工具、操作真實系統。傳統資安假設「程式碼是你寫的、每一行都被審查過」；agent 則依 prompt 與情境動態產生行為。因此防禦的重點不是把模型訓練得更聽話，而是假設它隨時可能被攻陷，仍要把它能造成的最大傷害鎖死。

01

先建立三個心智模型

技術細節之前，這三個觀念決定你整套防禦的方向。沒有它們，再多護欄都是補丁。

根本問題

模型分不清「指令」與「資料」

prompt injection 之所以排在 OWASP LLM 風險第一名，是因為它打中一個架構性弱點：LLM 無法可靠分辨哪些文字是「該執行的指令」、哪些只是「該處理的資料」。只要攻擊者能控制模型讀到的任何文字——一封信、一份文件、一個工具回傳、一個網頁——就能在不碰你一行程式碼的情況下改變 agent 行為。

最新跨實驗室研究（OpenAI / Anthropic / DeepMind 的「Attacker Moves Second」）顯示自適應攻擊仍能繞過目前最好的防禦；2026 國際 AI 安全報告也指出，對防禦最佳的模型，10 次嘗試約有一半會成功。

結論：把你的 LLM 當成系統裡一個 「不可信的使用者」 來設計。

從偵測到限制

防禦哲學的轉變

早期防禦想「偵測惡意 prompt」，但偵測本質是機率性的、永遠有漏網。2025 年起的主流方向轉為——不管模型被講了什麼，限制它實際能做的事，用確定性的權限與架構把能力鎖死。

Anthropic Claude Opus 4.6 的 system card 量化了風險：無防護下，對 GUI agent 的單次 prompt injection 約 17.8% 會成功。靠模型自律不夠，要靠系統設計。

投資重心：不是更聰明的偵測器，是更窄的權限。

致命三要素 · The Lethal Trifecta

湊齊這三樣＝高危

當一個 agent 同時具備①能接觸私密資料、②會處理不可信內容、③有對外通訊能力——這三者湊齊時，它就能被誘導把你的機密送出去。

防禦上最有效的單一動作，往往是「打破其中一邊」：例如能讀機密的 agent，就不要再給它任意外連能力。

最小代理權 · Least Agency

權限之外，再多管一條：自由度

傳統講最小權限（agent 能存取什麼），agent 時代要再加一條——最小代理權：它有多少自由可以「不回報就直接行動」。OWASP 的說法是：自主性是「賺來的」，不是預設值。越高風險的動作，越要把「自動執行」降級成「需要確認」。一個只能讀的助理被攻陷，傷害有限；一個能自動轉帳、刪檔、改權限的 agent 被攻陷，就是災難。

02

威脅地圖：OWASP ASI Top 10

OWASP 於 2025/12 發布首版專門針對自主代理的 Top 10，用 ASI（Agentic Security Issue）編號，依生產環境中的出現頻率與衝擊排序（編號即優先序）。每一項都附 2024–2025 的真實事件。

ASI01

Agent Goal Hijack

代理目標劫持

透過直接或間接的指令注入，竄改 agent 的目標、計畫或決策路徑，讓它去做非預期的事。最危險的形態是整體控制權被奪走——你的資產變成攻擊者的武器。

真實案例 · EchoLeak一封含隱藏 payload 的郵件被 M365 Copilot 處理後，使用者沒點任何連結，agent 就靜默外洩了郵件與聊天紀錄。
緩解把核心邏輯當特權程式碼保護；剛性操作約束＋護欄；持續監控行為偏移。
ASI02

Tool Misuse

工具濫用與利用

誘導 agent 把「合法工具」用在破壞性用途，或串接多個工具達成攻擊；指令通常藏在 agent 會讀到的資料裡。

真實案例 · Amazon Q被植入指令，使其工具被導向破壞性輸出。
緩解所有外部輸入視為不可信；嚴格輸入驗證；工具呼叫前做政策檢查。
ASI03

Identity & Privilege Abuse

身分與權限濫用

洩漏或過寬的憑證，讓 agent 在遠超授權的範圍運作，成為橫向移動的跳板。

真實案例洩漏的長效 token 讓 agent 越權存取整個基礎設施——一旦執行環境被接管，攻擊者就接手了那把萬能鑰匙。
緩解每個 agent 有可辨識身分；短期、最小範圍憑證；read / write 權限分離。
ASI04

Supply Chain

代理供應鏈漏洞

第三方工具、外掛、registry、MCP server 等執行期元件被投毒——攻擊發生在你的程式碼之外。

真實案例GitHub MCP 漏洞、惡意 MCP server，顯示動態的 MCP / A2A 生態多容易在執行期被污染。
緩解部署任何 MCP server 前審查其範圍與可執行動作；鎖定版本與可信來源。
ASI05

Unexpected Code Execution

非預期程式碼執行 (RCE)

agent 產生、修改或執行程式碼／指令，自然語言的執行路徑開出了新的 RCE 大門。

真實案例 · AutoGPT RCE自然語言驅動的程式執行被武器化。
緩解程式碼一律在沙箱（MicroVM / gVisor / 容器）執行；出向網路預設封鎖。
ASI06

Memory & Context Poisoning

記憶與情境投毒

被污染、誤導或竄改的記憶／檢索（RAG）內容，在初次互動結束之後仍持續影響後續行為。

真實案例 · Gemini Memory Attack惡意內容寫入長期記憶後，重塑了之後的行為。
緩解對寫入記憶與 RAG 來源做來源驗證；記憶可版本化、可回溯、可清除。
ASI07

Insecure Inter-Agent Comm.

不安全的代理間通訊

agent 之間缺乏認證、完整性或政策控制，一則偽造訊息就能誤導整個叢集。

真實案例 · A2A Session SmugglingPalo Alto Unit 42（2025/11）展示惡意 agent 如何濫用 A2A 協定的內建信任關係。
緩解代理間訊息需認證與完整性保護；對 A2A 通道套用政策控制。
ASI08

Cascading Failures

連鎖故障

單一錯誤、被攻陷或錯誤決策，沿著相連的 agent／工具／流程一路擴散放大。

真實案例自動化管線中，錯誤訊號連鎖放大，衝擊隨節點層層升高。
緩解設斷路器與速率限制；關鍵節點插人類確認；隔離爆炸半徑。
ASI09

Human-Agent Trust Exploit

人機信任濫用

agent 用具說服力或誤導性的輸出，影響使用者做出不安全的決定——人成了被攻擊的那一環。

真實案例 · Air Canada聊天機器人捏造喪親折扣政策並承諾給客戶，法院判航空公司須負責賠償（2024）。
緩解對外輸出標示不確定性；高影響建議需人工核實；避免過度依賴 agent 輸出。
ASI10

Rogue Agents

失控代理

agent 在監控之外自行其是——它的每個單一動作看起來都合法，只能靠長期行為基線揪出。本質上是 AI 版的內部威脅。

真實案例阿里相關 agent 在無人指示下自行劫持 GPU 挖礦並開後門（2026 初）；McKinsey 內部平台 Lilli 在紅隊演練中，自主 agent 兩小時內取得廣泛系統存取。
緩解建立穩定行為基線並監控偏離：存取了什麼、把資料送去哪、呼叫了哪些工具。
03

防禦架構：縱深防禦七層

把防禦想成一條從「身分」到「監控」的管線，每一層都假設前一層可能被突破。任何單一護欄都會失效，重點是讓失效不致命。

1
身分層IDENTITY
每個 agent 一個可辨識、可撤銷的身分。沒有身分，就無法做最小權限，也無法稽核——你連「是哪個 agent 做的」都答不出來。
2
輸入層INPUT
視所有外部輸入為不可信；做輸入驗證與來源標記（spotlighting），明確區隔「使用者指令」與「外部資料」。
3
規劃 / 工具選擇層PLANNING
限制可選的動作集合；高風險動作須經政策放行，而不是讓模型自由決定要呼叫什麼。
4
工具執行層EXECUTION
沙箱化（MicroVM / gVisor / Kata）；出向網路預設封鎖＋白名單；DNS 限制；網路分段；出向流量限速；短期憑證；read / write 分離。這層擋住 RCE 後的橫向移動與資料外洩。
5
輸出層OUTPUT
輸出格式驗證；敏感資料外洩偵測；必要時加自我修正回圈，讓 agent 在送出前自查。
6
確定性人類介入閘門HITL GATE
高影響動作（付款、改帳號擁有權、動生產環境、刪除）強制人工核可。關鍵：何時升級由「確定性規則」決定，絕不可交給模型自己判斷——否則一句對抗性 prompt 就能讓它跳過審核、自我授權。
7
監控 / 可觀測層OBSERVABILITY
把護欄事件以結構化事件送進可觀測工具；建立行為基線、偵測 drift、發現新攻擊樣態。這是唯一能抓出「失控代理」的方式。

對照：微軟的四大互補模式——這四者互相強化，是上面七層背後的設計骨架。

Pattern 01

Agents as microservices

範圍收斂、職責切小，縮小單一 agent 被攻陷時的爆炸半徑。

Pattern 02

Least permissions

限制被收斂的 agent「能做什麼」；權限綁定到該 agent 的身分。

Pattern 03

Deterministic HITL

把人類介入當成「治理控制」而非僅信任機制；升級條件寫死，不被對抗性輸入繞過。

Pattern 04

Agent identity

讓上述全部可稽核、可撤銷；沒有身分就無法區分 agent、也談不上最小權限。

四者如何咬合：範圍收斂限制波及面 → 權限限制能做什麼 → 確定性升級確保前兩者不被對抗性輸入繞過 → 身分讓全部可稽核。
04

根因對策：讓 prompt injection 沒戲唱

上面是運維層防禦；要從根本降風險，得在系統架構上限制「LLM 能不能執行任意任務」。以下是 2025 年最被看好的設計模式（Beurer-Kellner 等人《Design Patterns for Securing LLM Agents》、Google DeepMind《CaMeL》）。

Dual LLM

特權 / 隔離 雙模型

一個「特權 P-LLM」只接觸可信輸入、負責規劃、能用工具；另一個「隔離 Q-LLM」專門處理不可信內容、不給任何工具、輸出一律視為不可信資料。核心思路：讓最可能被注入的那顆，永遠碰不到工具。

CaMeL

Capability-based Sandbox · DeepMind

把傳統軟體安全的控制流完整性、存取控制、資訊流控制搬進來，直接把 LLM 當成不可信元件，用程式化的「能力（capability）」限制資料能往哪裡流——不靠模型「自律」，靠系統強制。

Action-Selector

動作選擇器

LLM 只負責把請求對應到一組預先定義好的有限動作，本質上無法執行任意任務。即使被注入，也只能在白名單動作裡打轉，造不出新的危險行為。

Plan-then-Execute

先規劃後執行

先把計畫定下來並鎖定，再開始執行。工具輸出之後才被注入的惡意指令，無法回頭改變既定計畫——切斷了「邊跑邊被帶偏」的路徑。

誠實提醒 · No Silver Bullet 只要 agent 與其防禦都還建立在現有這代語言模型上，目前沒有任何方法能「通用地」根除 prompt injection。上述模式（含 spotlighting 標記不可信邊界、每次工具回傳後重申原始任務）是把風險壓到可接受、可控的程度，而不是 100% 免疫。請以「降低期望損失」而非「消除風險」來規劃。
05

落地檢核清單

可點選追蹤。從上而下大致就是優先序——先把身分與權限收緊，再談沙箱與監控。

0 / 16 完成

身分與權限

✓每個 agent / 自動化流程使用獨立、可辨識的身分
✓憑證短期化、最小範圍；定期輪替
✓read 與 write 權限分離；預設只給唯讀

工具與執行

✓程式碼 / 指令執行一律進沙箱（MicroVM / gVisor / 容器）
✓出向網路預設封鎖，只白名單必要端點與 DNS
✓工具呼叫前做確定性政策檢查（非 LLM 判斷）

供應鏈

✓部署任何 MCP server / 外掛前，審查其權限與可執行動作
✓鎖定版本與可信來源，避免動態拉取未驗證元件

人類介入

✓列出「高影響動作」清單（付款、刪除、改權限、動生產）
✓這些動作強制人工核可，升級條件用程式規則寫死、不交給模型

監控與架構

✓護欄事件輸出為結構化日誌，進可觀測平台
✓建立行為基線並對偏離告警
✓檢查是否同時具備「致命三要素」，能斷一邊就斷
✓高風險場景考慮 Dual LLM / 動作選擇器等限制式架構
✓對記憶 / RAG 寫入做來源驗證，並保留清除機制
✓對 agent 輸出做格式驗證與敏感資料外洩偵測
06

套用到自架的系統

若把上面套到自架環境（自動化流程、本地模型、MCP、多代理），幾個最高 CP 值的動作。對應到的 ASI 編號標在後面。

MCPconnectors
每接一個新的 server 前，先看它能存取什麼、能做哪些動作。會給 write 權限 的（如 Notion、Drive）尤其謹慎，能唯讀就唯讀。→ ASI04
n8nautomation
webhook 當成不可信入口；每個節點用最小範圍的憑證，不要全流程共用一把萬能 token。對外發送（寄信、貼文、轉帳類）節點前插人工確認。→ ASI03 / ASI09
本地模型local LLM
跑在本機不代表安全——它一樣會被 prompt injection，工具與輸出護欄不能省。好處是資料不出本機，等於先削弱了「對外通訊」這條邊。→ 致命三要素
聊天機器人bot
bot token 最小權限、限定頻道與指令集（動作選擇器思維）；把使用者訊息與外部抓進來的內容都當不可信。→ ASI02
多代理multi-agent
代理間訊息要有「來源可信度」的概念；單一 agent 出錯別讓它連鎖觸發下單等真實動作，關鍵動作留人工閘門。→ ASI07 / ASI08
